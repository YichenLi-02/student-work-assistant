# Implementation Notes

Based on the project design pack v1.1 (documents 00–06 and 11, `openapi.json`, `database.sql`) and the implementation requirements set on 2026-10-19.

## Structure

```text
src/backend/app/
  main.py config.py db.py schema.sql security.py errors.py
  api/        core messages tasks documents drafts plans connections
  services/   import_service task_service reference_view document_service doc_rules
              style_service draft_service proposal_service planner plan_service chat_service
              analysis_service preferences privacy jobs
  providers/  net (outbound allow-list) tokens (keyring) oauth mail_readers calendars teams writers
  llm/        adapter (Responses API, strict JSON schema, no tool calls)
src/frontend/src/
  app/(App, i18n, context, time)  api/(client, types)  pages/(6 main entries + settings)
  components/(Panel, MailDetail, DraftEditor, ReviewDialog, DocumentLibrary, StyleReferences, AccountConnections, Tags)
  locales/zh-CN.json en.json  styles/(tokens.css, prototype.css, app.css)
```

Stack: one FastAPI process with SQLite (11 tables, following the design's `database.sql`); the frontend is React + TypeScript + Vite with plain CSS. No Redis, vector database, microservices or agent framework.

## Implemented (offline, no keys needed)

- **Sample import**: the 40 inbound mails and the 10 tone references are stored separately and de-duplicated by `(connection_id, provider_message_id)`, so importing again adds nothing. Category labels are stored as `reference_annotation` (suggested labels) and never shown as model output.
- **Mail page**: stat cards, topic categories, three filters (needs reply / needs action / important only, combined as an intersection), search, original text, source and evidence position, user corrections (stored as `user`) and an activity log.
- **Tasks**: the 32 time expressions are merged by `entity_key`; each keeps its evidence, checked word for word against its position in the original. When dates conflict, every candidate is kept and the official date stays empty; an unstated time stays null. A submission receipt only marks its own deliverable as done; times that are not tasks (code lifetimes, promotion ends and so on) never become tasks. Confirming a task needs a date, a time, a time zone or a planning cutoff, and an effort estimate, and carries a revision number so that an old page cannot overwrite it. Actual progress is recorded as idempotent events.
- **Course documents**: real PDF upload, parsed page by page with pypdf so page numbers are kept. Scanned, encrypted and unparseable files are marked `needs_ocr`, `encrypted` and `failed`, and the text can be pasted instead. Pasted text is stored separately as `user_pasted` and never treated as parsed PDF text. Local rules extract explicit dates and times; relative dates such as "the Friday after reading week" or "Week N" are resolved only against the academic calendar of the same term, and the calendar itself never creates tasks. Excluding a document sends its tasks back to review and makes plans that depend on it stale; local data can also be deleted.
- **Study plan**: a deterministic earliest-deadline-first planner with an independent validator that checks the daily cap, minimum and maximum session length, breaks, the deadline buffer, weekly flex time and available hours. A plan is `infeasible` only when the capacity upper bound is already below the demand; otherwise it reports `needs_adjustment`. Completed progress reduces the remaining work and counts towards that day's cap. Re-planning shows the differences and marks the old plan stale. A failed calendar read is never treated as free time.
- **Group work**: a pasted discussion is sorted by rules into suggestions, decisions, action items and open questions. Only an explicit decision sentence, or a task the owner confirmed, counts as a decision; an unknown owner or date stays null. A Teams follow-up message can be drafted from the result.
- **Personal tone**: only text the student wrote is used (from M49 only the first sentence, not the Zoom template). Each sample can be included or excluded; after a change, pending proposals that depend on it are invalidated, and draft text is not replaced but must be checked again. Recruiting and Chinese have no own samples, so a generic tone is used and labelled as such.
- **Drafts and approval**: every unverified fact stays a `[[placeholder]]`; nothing is invented. A proposal stores an immutable payload, its SHA-256 hash, a revision number and an expiry, and is bound to the session. Confirming requires the same hash and an Idempotency-Key, and the backend uses a conditional UPDATE so it runs only once. Any change voids an earlier approval. The offline version only records `simulated`.
- **Security**: session cookie (HttpOnly, SameSite=Strict), CSRF check on writes, Origin allow-list; outbound requests only go to fixed official domains and Canvas / instructure is always refused; mail addresses, links, phone numbers, codes and long numbers are removed before storage.
- **English and Chinese**: the interface language is stored in preferences; mail, evidence, samples and the user's own text stay in their original language.

## Planning rules added after the group review on 2026-11-05

- **The daily cap covers the whole day**: progress already recorded on any task that day, plus study blocks already written to the calendar that have not started or are in progress, all use the day's allowance. Selecting only some tasks, switching tasks or regenerating all use the same allowance.
- **Written study blocks are not scheduled twice**: a plan reads both the main calendar and the app's dedicated study calendar. Every future study block the app actually wrote (from any plan) is kept, uses the allowance and is subtracted from its task's remaining work; saving only submits the new part. If a block is no longer in the study calendar (most likely you deleted it), it counts as unscheduled; if the study calendar cannot be read, the write records are kept, so the plan schedules too little rather than twice.
- **Logging progress needs a task**: "Log progress" on the plan page requires choosing a task and entering the actual minutes; before saving it says how many minutes go to which task, and afterwards it shows what remains. Submitting the same request twice counts once.
- **Free/busy is checked again before writing**: when writing to the study calendar is confirmed, the backend reads the relevant calendars again. A new conflict, or a failed read, stops the write, lists the clashing times and makes the plan stale; the review screen links straight to "Conflicts and fixes" to compare suggestions before reviewing again. This shortens the window for conflicts but cannot guarantee perfect synchronisation across systems.
- **Validator corrections**: after written blocks are subtracted, a remainder under 30 minutes may be placed as one short session (the validator used to judge it by the amount before subtraction and flagged it wrongly). When the greedy planner met a meeting shorter than the break, the second session used to start after only the meeting's length; it now waits for the full break.
- **Exact search when the greedy plan falls short**: each task is first placed the old greedy way (60-minute target per session, as early as possible); when everything fits, the result is exactly the same as before. When it does not, every feasible way of splitting that task is searched and the one that places the most minutes is taken (ties: more on earlier days, sessions closer to 60 minutes). The overall result is never worse than the greedy one. When several tasks do not fit in deadline order, other orders are tried; the first order that fits everything is used (each task must still finish before its own deadline buffer), otherwise the earliest deadline keeps priority.
- **Per-task daily cap**: besides the overall daily cap (all tasks together), a separate rule limits how many minutes one task may get in a day ("Per-task daily cap" in Settings, default 120; 0 means no separate limit; it cannot be below the minimum session length). Progress already logged on that task that day and its written blocks count towards it; the planner (greedy and exact search), the validator, the capacity proof, conflict repair and manual editing all respect it. With the overall cap raised to 4 hours, one task still gets at most 2 hours and the rest is left for other tasks. When this rule is what stops a task fitting before its deadline, the plan says so ("limited by the per-task daily cap: at most X minutes can be placed before the deadline"); in manual editing it is a soft rule the student must accept explicitly; and the repair suggestions show how much more "per-task daily cap +30 minutes" would place (marked as relaxing a rule, never recommended).
- **Evaluation**: `src/backend/evaluation/` holds 27 fixed scenarios with hand-written expectations (`scenarios.json`; S25–S27 target the per-task daily cap) and 200 fixed-seed random scenarios (some with a random per-task daily cap). `scripts/eval-planner.py` writes `report.json` and `report.md` to `local-data/planner-eval/`. The metrics are computed by the evaluation code independently of the planner's own validator; besides violations it reports coverage, unplaced minutes and the gap between single-task scenarios and an optimum found independently by exhaustive search (currently 0 for all). The global optimum of multi-task scenarios is not proven by exhaustive search.
- **Date and time inputs**: the browser's native date control follows the system language, not the interface language, so custom date and time inputs are used; they keep the native formats and switch with the interface language.

## Plan conflicts (added after the second review)

Approach: **find the conflict → explain it → offer 2–3 fixes with the fewest changes, each with its cost → the student chooses or edits by hand → nothing is written until the usual review and confirmation**. The system never changes a plan silently and never relaxes the student's rules on its own.

- **Finding conflicts** (checked once automatically when the plan page opens; also via "Conflicts and fixes → Check for conflicts", or "Find a fix for this conflict" when a write is stopped in review): checking, fix suggestions and manual editing re-read the plan's own calendar source, account and date range, so a calendar chosen on the page for the next plan is never mixed in; once the plan's dates are past, nothing is read and a new plan is suggested; the interface shows when and how it last checked. It re-reads the calendar and lists which study blocks (suggested, locked or written to the study calendar) overlap which events; with no clash but not enough time before a deadline, it says how many minutes are missing. Read-only; nothing is changed.
- **Fix suggestions** (`app/services/repair.py`, pure functions with no database or network access): each suggestion is a complete candidate plan produced by running the same planner and validator with a different choice of which blocks stay fixed:
  - Move only the affected blocks: every other block stays exactly where it is; the clashing block is first moved whole, then split if needed;
  - Let later deadlines give way: tasks with later deadlines give time to the earliest one;
  - Re-plan the whole week: only blocks the student locked are kept;
  - Use this week's flex time / study 30 minutes more that day: these relax the student's rules, so they are clearly marked "relaxed", appear only when they place more work than every rule-keeping option, and are never "recommended".
  - Ordering: rule-keeping options first, then fewest unplaced minutes, fewest blocks changed and largest distance from the deadline buffer; an option that is no better on any of these is not shown; at most 3. If even the best option cannot place everything, a link to draft an extension request is offered as well (reviewed by the student before sending).
- **Student choice**: candidate plans are first saved as "suggestions not chosen" and cannot be saved to a calendar directly; choosing one makes it the current plan and voids the others (if the original plan was replaced, the student is asked to check again; if the calendar, tasks or settings changed meanwhile, the choice is refused and a new check is required).
- **Manual editing**: every study block can change its start time and length, be deleted or be unlocked. Hard limits are refused with the reason: overlapping a calendar event or another study block, past the deadline, already in the past, crossing midnight, outside the plan's dates, or a length outside 5–240 minutes. Soft rules (session length, breaks, daily cap, deadline buffer, study hours, flex time) are listed first and only saved after the student clicks "Save anyway"; an accepted exception applies only to that block and is shown with the plan. Edited blocks are locked and stay put in later re-plans and repairs; making a block longer takes the extra time from later unlocked suggestions of the same task, so nothing is scheduled twice.
- **Written blocks can be moved too**: only inside the app's own study calendar and only blocks of that task in this plan. The review screen lists both "create" and "delete (moved)"; after confirmation the new event is created first and the old one deleted afterwards; the deletion result is recorded separately, an event that no longer exists counts as done, and when the network result is uncertain the student is asked to check the calendar. The pre-write free/busy check ignores the old block being moved, so it is not mistaken for a conflict. The main calendar and other calendars are never changed.
- **Did you finish it?**: study blocks that were written and ended within the past week are shown on the plan page with "Done / Partly done (enter minutes) / Not done". The answer is added to the task's progress (once per block), then a re-plan is suggested; "Not done" adds no progress and the remaining work is scheduled again at the next re-plan.
- **Offline demo**: in demo mode "Simulate a new meeting" adds a meeting to the sample calendar only (stored in the local `demo_busy` table and removable in one click) and checks for conflicts automatically, so the whole flow can be shown without a real calendar.
- **Evaluation**: the report of `scripts/eval-planner.py` has a "Conflict repair" section: in the 200 random scenarios, every scenario with a plan gets a new meeting dropped on a study block (some on written blocks), and the recommended option is checked with the same independent metrics as the planner evaluation. Current results: 191 scenarios, 0 hard-rule violations (including the per-task daily cap); unplaced minutes are never more than with a full re-plan; in the 189 scenarios where both place the same amount of work, the recommended option changes 1.29 blocks on average against 1.67 for a full re-plan, and never more; the recommended option relaxes a rule in 0 scenarios; all 4 scenarios where the new meeting hit a written block got a move.
- New endpoints: `POST /api/plans/{id}/conflicts`, `/repair-options`, `/adopt`, `/edit-block`; `GET/POST /api/study-checkins`; `GET/POST/DELETE /api/demo/busy`. Tests: `tests/test_conflict_repair.py`; evaluation assertions in `tests/test_planner_eval.py`.

## Calibrating estimates from check-ins (added after the second review)

Approach: **suggest estimates from the student's own history, and change nothing until the student accepts**. The rules are in `app/services/calibration.py` (pure functions), storage in `calibration_service.py`, and the interface is "Estimates from your own history" on the plan page.

- **Data**: the first estimate entered for a task is stored separately and never overwritten, so calibration always compares against the student's original estimate. Marking a task done asks "Roughly how many minutes did it actually take?" (the student can choose "not sure", in which case the logged progress is used and labelled as such). Each "Did you finish it?" answer is stored with the planned length of that block.
- **Estimate bias**: a suggestion needs at least 3 completed tasks. The same course is used first; with fewer than 3 there, tasks of the same kind (submission, exam, reply); then all tasks. The median of "actual time / original estimate" is used, with each task's ratio limited to 0.25–4 so one extreme task cannot dominate. Biases under 15% are not shown. Only unfinished tasks still at their original estimate get a suggestion; tasks whose estimate the student already changed do not. Suggestions are rounded to 15 minutes, at most double or half, and never below the time already spent.
- **More careful when shortening**: suggesting less time needs at least 5 completed tasks and closes only half the gap. Underestimating means missing a deadline, overestimating only wastes a little time, so the costs of the two directions are not equal.
- **Estimate used up but not finished**: when the logged time reaches the estimate, the plan has no work left to place and the task would silently disappear from it. So the system asks "Are you done?": "Done" marks it complete, "Not yet, I need N more minutes" sets the estimate to the time used plus N.
- **Completion rate**: answered study blocks from the last 28 days are used to compute how much of the planned time was actually done. With at least 5 answers and a rate below 85%, it suggests raising the weekly flex time to roughly cover the time not done each week (rounded to 30 minutes, at most +180).
- **The student decides**: every suggestion offers "Change to X minutes / Keep Y minutes / Show the basis", and the basis lists the tasks used with their estimates and actual times. Accepting changes the estimate only through the normal task update (with its version check), which makes the existing plan stale, and the interface offers "Re-plan" directly. A task that has been answered once is not asked again. The server uses its own recomputed suggestion and does not trust a number sent by the frontend.
- **Sample data**: when sample data is shown, "Load sample history" adds 4 synthetic completed tasks and 8 synthetic check-ins; the demo then suggests 360 → 465 minutes for the sample report and a higher flex time, and everything can be removed in one click. With sample data turned off, these synthetic records never enter real calibration.
- **Evaluation (simulated, not real students)**: the report of `scripts/eval-planner.py` has an "Estimate calibration" section. 200 simulated students (one third accurate, one third habitual under-estimators, one third habitual over-estimators, each task with random variation) complete 8 tasks each, and every suggestion uses only tasks finished earlier. Among tasks that got a suggestion, the median estimate error falls from 24.2% to 17.8%; for under-estimators from 26.4% to 15.7%, and tasks "estimated at under 80% of the actual time" from 226 to 60; for over-estimators from 38.3% to 28.0%, and because shortening only closes half the gap, new clear under-estimates rise only from 3 to 6; accurate students are essentially unchanged. These parameters are assumptions; they show the direction and safety of the rules, not real-world accuracy. "Close only half the gap" was chosen from this simulation: shortening all the way would lower over-estimators' error further, but clear under-estimates would rise from 3 to about 40.
- New endpoints: `GET /api/calibration`, `POST /api/calibration/decide`, `POST /api/calibration/overrun`, and for sample data `POST/DELETE /api/demo/calibration-history`; the task update endpoint gains `actual_minutes`. Tests: `tests/test_calibration.py`; assertions for the simulation in `tests/test_planner_eval.py`.

## Outlook dedicated study calendar (added after the second review)

- **What it does**: as with Google, an Outlook account can grant "Dedicated study calendar"; the app then creates its own calendar in Outlook (only after review and confirmation, and never a second one for the same account). Writing study blocks, moving them (create the new one, then delete the old one), the free/busy re-check before writing, reading written blocks back at the next plan and "Did you finish it?" all work the same way.
- **Where it writes**: study blocks go to the study calendar of the account whose free/busy produced the plan; if that account has no study calendar, they go to the other account that has one. The review screen states "Write to: the app's study calendar in Outlook" or "in Google Calendar". Every written block records its account; a moved block is deleted from its original account, so a block written to Google can be moved to Outlook.
- **Writes only to its own calendar**: every Graph write goes through one path function and can only target `/me/calendars/{the app's calendar ID}/events`; deletions also happen only in that calendar. When the old calendar ID is unknown it does not guess, and it never reports a block it did not delete as deleted. The main Outlook calendar (`/me/calendarView`) is read-only; the study calendar is read back separately through `/me/calendars/{id}/calendarView`.
- **Request details**: events have no attendees (no invitations are sent) and are marked busy; times are converted to UTC before they go to Graph, so Windows and IANA time-zone names cannot disagree; each event carries a `transactionId` derived from the proposal and its sequence number, so a network retry does not create a duplicate in Graph.
- **Permissions**: Microsoft has no narrow permission like Google's `calendar.app.created`, so `Calendars.ReadWrite` is needed, and it can change every calendar. In the presentation this should be stated honestly: writing only to the app's own study calendar is a limit in the code, not in Microsoft's authorisation; students who do not want to grant it can use the Google study calendar only.
- Tests: `tests/test_outlook_study_calendar.py` runs authorisation, calendar creation, writing, reading back and moving against a simulated Graph API and asserts that no write request goes anywhere except the study calendar. For a real account, `scripts/check-outlook.py --live` checks read-only whether the study calendar exists and can be edited.

## Provider code and how it was verified

- Model adapter: OpenAI Responses API, `store=false`, strict schema; the source ID, verbatim quotes and date formats are checked locally, and results are cached by content hash, prompt, schema and model version. When it is not enabled it returns 409 and the offline features are unaffected.
- Google OAuth (PKCE + state, incremental authorisation); Gmail read-only sync (paging, bounded retries, Retry-After, a single failed mail counted as partial completion); Google freeBusy.
- Microsoft OAuth (PKCE, `common` tenant by default, so personal Outlook and school accounts can both sign in) and Graph reads of mail, calendarView and Teams chats (only chats the user selects). Outlook sync filters the inbox by time range (optionally Junk Email and Deleted Items), pages automatically, de-duplicates by immutable ID, records only attachment names and sizes, and "Open original" uses the webLink returned by Graph. Microsoft error codes (AADSTS) are shown on the connection card with how to fix them. Setup and the real-account check are in `docs/OUTLOOK_SETUP.md` and `scripts/check-outlook.py`.
- Real write executors: Gmail send, Graph sendMail (with attachments up to 3 MB in total), Teams chat messages, and the Google and Outlook dedicated study calendars and their events. A timeout is recorded as `unknown` and never resent automatically; a 202 is recorded as `accepted`, which does not mean delivered; event IDs are deterministic and partial success is recorded item by item.

All of this was first built and tested against simulated HTTP. Since then, Gmail read and reply, Google Calendar free/busy, Outlook mail and calendar reads, and writes to the Outlook study calendar have been tried with real accounts (see `docs/OUTLOOK_WRITE_VERIFICATION_20261106.md`). Teams has not been tried with a real school account.

## Differences from the design contract (`openapi.json`)

| Where | Difference | Reason |
|---|---|---|
| `GET /api/messages` | Response adds `counts` | The stat cards need counts that do not depend on the filters |
| MessageSummary | Adds `source_type`, `attention_label`, `uncertainty`, `analysis_status`, `excluded`, `attachment_count`, `split` | Cards show what needs checking and where it came from |
| `analysis_origin` | Adds `rule` | Local rule results must not be labelled model or none |
| Document upload | `POST /api/uploads` plus `POST /api/documents` (JSON metadata) instead of `/api/imports` | Metadata and the permission statement are validated together; `/api/imports` is only for samples |
| Document | Adds `pages`, `page_count`, `user_excerpt`, `parsed_text`, `extraction_error`, `upload_id`, `synthetic`, `candidates` | Page numbers are traceable, and pasted text is kept apart from parsed text |
| `/documents/{id}/extract` | Returns the result synchronously; `use_model=true` returns 422 | Local rules are fast; model extraction from documents is out of scope for this version |
| Draft | Adds `purpose`, `placeholders`, `style_mode`, `style_note`, `relationship`, `language`, `stale_style`, `generation`, `recipients_deidentified`; requests may send `relationship`, `language`, `use_model` | Tone fallback and placeholders need explicit state |
| Plan | Adds `per_task`, `busy`, `days`, `stale_reasons`, `synthetic`, `computed_status` | The interface shows each day's schedule and why a plan is stale |
| ChatSummary | `analysis_origin` may be `rule`; adds `followup_points`, `messages`; requests may send `raw_text` | Pasted text is parsed by the backend |

## Still simulated or synthetic

- In demo mode the planner's busy times come from a synthetic timetable (`provider=mock`), and the report task is synthetic (DEMO5105, 2026-10-23 17:00).
- A synthetic course outline and academic calendar (Demo Term A, not the official NUS calendar) and a synthetic group discussion.

## Known limitations

- The group discussion is organised by keyword rules, so complex Chinese and English phrasing can be missed; with a model connected, chat organising still needs its own structured call (P07). In this version only mail analysis and drafting use the model.
- No OCR for PDFs.
- Calendar writes only create study blocks in the app's dedicated study calendar (Google or Outlook), or move them there (create + delete) after the student confirms; other calendars are never changed. The Outlook write permission `Calendars.ReadWrite` is broader than what is used, and "writes only to its own study calendar" is a limit in the code.
- Asia/Singapore has no daylight saving time; edge cases involving daylight saving have not been tested.
